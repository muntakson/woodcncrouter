Grbl Sender API reference

Every HTTP call between the Android app (Grbl Sender, org.dnaboy.grblsender) and this backoffice: what the app sends, what it expects back, the commands it accepts from the remote-control API, and the dashboard endpoints that read what it uploaded. The examples use this server: .

Base URLSet on the tablet in Settings → General → Backoffice server. Default https://cnc.iotok.org (built into the APK as LOG_SERVER). On the LAN: http://192.168.219.157:3077.
FormatJSON request and response bodies (Content-Type: application/json) unless stated. Timestamps are Unix epoch milliseconds. Responses carry Cache-Control: no-store.
ErrorsJSON {"error": "…"} with a 4xx/5xx status. Exception: auth failures answer 401 with plain text and a WWW-Authenticate: Basic challenge.

Authentication

Four access levels. The tablet itself only ever uses the first two.

LevelHowUsed by
publicNo credentials.App: version check, release history, APK, firmware and G-code downloads.
ingest keyHeader X-Ingest-Key: <INGEST_KEY>. The key is compiled into the APK from backoffice/.env at build time.App: log upload and the remote-control sync loop.
adminOpen from the LAN (192.168.x, 10.x, 172.16–31.x, localhost). Through the public proxy: HTTP Basic DASH_USER / DASH_PASSWORD.This dashboard and this page.
admin or API keyAdmin as above, or header Authorization: Bearer <CNC_API_KEY>.Scripts and other servers that drive the machine.
Requests that arrive through nginx (they carry X-Real-IP) are never treated as LAN, so a public request always needs Basic auth or the API key, whatever its source address.

How the app talks to the backoffice

Log uploadThread remote-log: queues every app log line (max 5000), posts batches of ≤500 to /api/ingest about every 0.5 s while there is traffic. On failure it keeps the lines and retries with backoff 1 → 30 s.
Remote syncThread remote-sync: loops on /api/device/sync with a 1.5 s long-poll. Sends status, console lines, command results and job events; receives commands. Retries with backoff 2 → 30 s. The title-bar chip shows Backoffice / Offline.
Update checkAt start-up, and whenever an ingest reply's latestVersionCode is newer than the installed build: /api/version. Download: /apk/latest.apk.
CameraClass CameraStreamer: idle until a viewer watches. The sync reply's camera.want starts it; then threads camera-upload (encode) and camera-send POST one JPEG per request to /api/device/frame. Each frame reply says whether anyone is still watching. Viewers: MJPEG, frame long-poll, snapshot.
On demandSettings → Firmware: /api/firmware, /firmware/…. Settings → Files and remote load/run: /api/gcode, /gcode/…. Server Test: /health + /api/version on the typed URL.

Remote commands the app executes

Queued with POST /api/cnc/command and delivered in the reply to the tablet's sync. The app runs each command on its UI thread and reports {"id", "ok", "msg"} in its next sync. A command the tablet has not collected within 30 s expires on the server. If a command is older than 20 s when it arrives (age), the app refuses it.

Checks, in this order

  1. Remote control switch (Settings → General, pref remoteControl, default on). When off, only hold, stop and status run. The server already answers 403 for the rest when the last status said remoteControl:false.
  2. Controller connected: every command except status and load needs the USB link → "the controller is not connected to the tablet".
  3. Job running: only hold, resume, stop, reset, status and send with ! ~ ? → "a job is running – only hold, resume and stop are accepted".

The status object

Built by the app (MainActivity.publishStatus, at most every 250 ms) and sent with every sync. The server stores the latest one per tablet, adds at (receive time), and returns it as status from /api/cnc/status.

Job-log events

The tablet keeps its own job log (files/jobs.json, Settings → Job log) and uploads each event once with the sync. uid makes uploads idempotent. Read them back with /api/jobs.
